# 首页加载与性能

首页保留同一段山景、241 帧时间轴和三章滚动叙事。视频转换移到发布前，访客不下载 MP4，也不运行视频解码 Worker。

## 加载规则

- 发布资源：1280×720 WebP，241 帧约 4.13 MB，按版本哈希命名并缓存一年；文件哈希记录在 `frames-manifest.json`。
- 当前帧优先，沿滚动方向预取最多 8 帧、反方向最多 3 帧；首次停在首屏只加载附近 9 帧，不等待整段动画。
- 最多 4 个并行下载/图像解码，最多 24 个 ImageBitmap；HTTP 缓存可以复用已访问的帧。
- 首页先显示封面，按钮和文字立即可用，第一帧就绪后淡入。请求失败或初始准备超过 5 秒时切换为可正常阅读的静态页面。
- 触屏、窄屏、减少动态效果或图像解码不可用时使用静态页面。浏览器报告省流量或 2G 时直接使用静态页面；其他网络根据实际下载表现判断：连续两张小帧下载各耗时至少 700ms 时回退静态阅读，避免持续卡顿。浏览器带宽估计不用于自动切换，以免误判。
- 页面隐藏或首页不可见时暂停并取消未完成下载；静止且附近帧就绪后不空转；进入工作台后中止请求并释放全部图像资源。

网络能力信息是浏览器估计，不是测速承诺。1280×720 是此次体积与清晰度的选择，超大屏放大会比原视频柔和；没有改变构图或叙事时间轴。

## 发布前预处理

仓库已包含可直接运行的帧资源，正常安装和构建不需要原始视频或额外服务。仅重新生成媒体时需要：

```bash
npm run prepare:home -- /path/to/authorized-original.mp4
```

脚本使用开发依赖 esbuild、Playwright 和 MP4Box，在本地临时页面中一次性转换，输出版本化帧和清单。需要安装 Google Chrome；或安装 Chromium 后设置 `PLAYWRIGHT_CHANNEL=chromium`。源文件必须与已确认视频哈希匹配；替换素材时应同时明确更新来源、版权和验收。

## 性能验收

先 `npm run build`、`npm run start`，再执行：

```bash
node scripts/check-home-performance.mjs
# 正式环境：
node scripts/check-home-performance.mjs --url=https://whitespace-junz11055-8124.vercel.app
```

固定检查三类场景：冷缓存、同一浏览器缓存访问，以及 4 倍 CPU 限速 / 1.6 Mbps / 150ms 网络延迟。正常网络检查完整慢滚、快滚和反向滚动，限速场景检查静态阅读与规划入口。

验收门槛：正常场景导航到首个动画帧小于 3 秒，帧准备小于 5 秒，首屏附近帧总量小于 400 KB、数量最多 17 帧，绘制间隔 P95 不高于 100ms；静止空转为 0，图像缓存最多 24；限速场景下载最多 8 张探测帧后回退，10 秒内页面可读且规划可进入。报告记录实际环境和数值，不将本地结果宣称为所有网络保证。

此前真实 CDN 样本需要约 9.4 秒下载和 17.2 秒整段转换，总计 26.6 秒才完成帧库。这个旧指标是“完整帧库就绪”，新指标是“首个动画帧可见”，二者定义不同；新实现已直接移除访客端整段转换。


2026-09-08 本地生产样本（正常网络固定为 10 Mbps / 20ms）：冷缓存导航到首帧 922ms，帧准备 185.5ms；首屏9帧共330746字节。缓存访问导航到首帧871ms，帧图片网络传输0字节。慢滚绘制间隔P95为34.3ms、快滚17.7ms、反向17.3ms，未记录长任务，静止空转0。受限场景下载5张探测帧后回退，约2847ms可正常静态阅读。以上为单次本地实验，不代表所有公网访问速度。
